## q_c003_01
- type: choice
- kp: SQL 基础
- difficulty: easy
- score: 5
- stem: 查询 student 表中 age 大于 18 且 gender 为"男"的记录，正确的 SQL 是？
- options: A) SELECT * FROM student WHERE age>18 AND gender='男' B) SELECT * FROM student HAVING age>18 C) SELECT * FROM student WHERE age>18 OR gender='男' D) SELECT * WHERE age>18 AND gender='男'
- answer: A
- analysis: 过滤行用 WHERE 且多个条件用 AND 连接（同时满足）；OR 表示任一满足，语义不符；HAVING 用于分组后的过滤；D 缺少 FROM 子句。

## q_c003_02
- type: choice
- kp: SQL 基础
- difficulty: easy
- score: 5
- stem: 聚合函数 COUNT(*) 与 COUNT(列名) 的区别是？
- options: A) 完全相同 B) COUNT(*) 统计所有行，COUNT(列名) 不统计该列为 NULL 的行 C) COUNT(列名) 更快 D) COUNT(*) 只统计非空行
- answer: B
- analysis: COUNT(*) 统计行数（含全 NULL 行）；COUNT(列名) 对该列做非空判断，NULL 不计入。COUNT(1) 与 COUNT(*) 在现代 MySQL 优化器下性能无差别。

## q_c003_04
- type: choice
- kp: MySQL 索引
- difficulty: medium
- score: 5
- stem: 联合索引 (a, b, c)，下列哪个查询能完整用到该索引的最左前缀？
- options: A) WHERE b=1 AND c=2 B) WHERE a=1 AND b>10 C) WHERE c=3 D) WHERE b=1
- answer: B
- analysis: 最左前缀原则：查询条件必须从索引最左列开始连续命中。B 从 a 开始且 b 为范围查询可用到 (a,b)；A、D 跳过了 a 无法使用该索引；C 同样跳过。

## q_c003_05

- stem: 下列哪种写法会导致索引失效？
- options: A) WHERE name = 'tom' B) WHERE LEFT(name,3) = 'tom' C) WHERE age = 20 D) WHERE name LIKE 'tom%'
- answer: B
- analysis: 对索引列使用函数或运算（LEFT/UPPER/列+1 等）会使优化器无法走索引。LIKE 'tom%' 前缀匹配可以走索引，'%tom' 后缀匹配不行。

## q_c003_08
- type: choice
- kp: 事务与锁
- difficulty: hard
- score: 5
- stem: InnoDB 在 REPEATABLE READ 隔离级别下，同一事务内两次相同的普通 SELECT 读到的结果？
- options: A) 可能不同（不可重复读） B) 相同（MVCC 快照读） C) 总是最新数据 D) 会阻塞
- answer: B
- analysis: InnoDB 默认隔离级别 REPEATABLE READ 通过 MVCC 实现快照读：事务开始后第一次查询建立 ReadView，后续普通 SELECT 读取同一快照，两次结果一致，避免了不可重复读；当前读（SELECT...FOR UPDATE）则读最新版本。

## q_c003_13
- type: short
- kp: MySQL 索引
- difficulty: medium
- score: 10
- stem: 简述为什么 InnoDB 选择 B+树而不是哈希表作为索引结构。
- keywords: 范围查询, 排序, 等值查询, 树高, 磁盘 IO
- analysis: 哈希表只支持等值查询，无法支持范围查询（BETWEEN、>、<）和排序。B+树叶子节点有序且通过双向链表相连，范围查询和排序高效；且 B+树矮胖（千万级数据树高 3~4 层），每层一次磁盘 IO，IO 次数可控。等值查询上两者都接近 O(1)~O(log n)，综合场景 B+树更优。

## q_c003_14
- type: short
- kp: 事务与锁
- difficulty: medium
- score: 10
- stem: 什么是脏读、不可重复读和幻读？InnoDB 默认隔离级别能避免哪些？
- keywords: 脏读, 不可重复读, 幻读, REPEATABLE READ, MVCC
- analysis: 脏读：读到其他事务未提交的数据；不可重复读：同一事务内两次读同一行结果不同（他人 update 提交）；幻读：两次范围查询行数不同（他人 insert 提交）。InnoDB 默认 REPEATABLE READ，通过 MVCC 避免脏读和不可重复读，并通过间隙锁+MVCC 在很大程度上避免幻读。

## q_c003_16
- type: short
- kp: 面试
- difficulty: hard
- score: 10
- stem: 【面试题】什么是回表？什么是覆盖索引？如何利用覆盖索引优化 SELECT name FROM user WHERE age=25？
- keywords: 回表, 覆盖索引, 联合索引, 二级索引, 主键
- analysis: 回表：二级索引叶子节点只存索引列+主键，查询需要的列不在索引中时，需拿主键再回聚簇索引查整行。覆盖索引：查询所需列全部包含在索引中，无需回表。优化方式：建立联合索引 (age, name)，WHERE age=25 且 SELECT name 均可从索引获得，EXPLAIN 的 Extra 显示 Using index，性能显著提升。

## q_c003_20
- type: short
- kp: 面试
- difficulty: hard
- score: 10
- stem: 【面试题】为什么说"索引不是越多越好"？从写性能和存储两个角度说明。
- keywords: 写入开销, 维护 B+树, 存储空间, 优化器选择, 区分度
- analysis: 1) 写性能：每次 INSERT/UPDATE/DELETE 都要同步维护所有相关索引的 B+树结构，索引越多写放大越严重；2) 存储：每个索引都是一棵独立的树，占用磁盘与内存缓冲池空间，挤占热点数据缓存；3) 优化器：索引过多增加优化器成本，低区分度索引（如性别）还可能被误选导致更慢。原则：只为高频查询条件建索引，优先联合索引，控制单表索引数量。
