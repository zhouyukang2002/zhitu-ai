## q_c008_01
- type: choice
- kp: Redis 数据结构
- difficulty: easy
- score: 5
- stem: 存储用户最近浏览的商品 ID 列表（ newest 在前，最多 50 条），最适合的结构是？
- options: A) String B) Hash C) List（LPUSH + LTRIM） D) Set
- answer: C
- analysis: List 的 LPUSH 头插保持最新在前，LTRIM 截断保留 50 条，天然契合"最近 N 条"场景。Set 无序，Hash 适合对象字段。

## q_c008_04
- type: choice
- kp: 缓存策略
- difficulty: medium
- score: 5
- stem: 请求大量不存在的 ID（如 -999）穿透缓存打到数据库，最有效的组合方案是？
- options: A) 只有过期时间 B) 空值缓存 + 布隆过滤器 C) 加大数据库连接池 D) 关闭缓存
- answer: B
- analysis: 缓存穿透治理：1) 不存在的 ID 缓存空值（短 TTL）拦住重复攻击；2) 布隆过滤器在缓存前拦截"一定不存在"的 key；3) 接口层参数合法性校验。单靠过期时间无效。

## q_c008_05
- type: choice
- kp: 缓存策略
- difficulty: hard
- score: 5
- stem: 热点 key 过期瞬间，成百上千请求同时查库并回填缓存，这种现象叫？
- options: A) 缓存穿透 B) 缓存击穿 C) 缓存雪崩 D) 缓存污染
- answer: B
- analysis: 击穿是"单个热点 key 过期瞬间"的并发重建问题。治理：互斥锁（只允许一个请求重建）或逻辑过期（物理不过期+异步刷新）。雪崩是"大量 key 同时过期或 Redis 宕机"，治理靠 TTL 随机抖动与高可用集群。

## q_c008_07
- type: choice
- kp: 缓存一致性
- difficulty: hard
- score: 5
- stem: 更新数据时"先更新数据库，再删除缓存"方案中，仍可能出现不一致的窗口是？
- options: A) 不可能出现不一致 B) 更新库成功但删缓存失败/删除前有旧值读入 C) 删除缓存失败会自动重试 D) 数据库主从延迟不存在
- answer: B
- analysis: 该方案的不一致窗口：1) 删缓存失败（需重试/消息补偿）；2) 读写交错：读请求在更新库前命中旧缓存，写库+删缓存完成后才回填旧值（低概率，可用延迟双删/订阅 binlog 缓解）。追求强一致需要分布式锁串行化，成本高，通常接受最终一致。

## q_c008_08
- type: choice
- kp: 持久化
- difficulty: medium
- score: 5
- stem: RDB 与 AOF 的对比，正确的是？
- options: A) RDB 记录每条写命令，AOF 记录快照 B) RDB 是某时刻的内存快照（紧凑恢复快），AOF 记录写命令（更完整但文件大） C) 两者不能同时开启 D) AOF 恢复一定更快
- answer: B
- analysis: RDB 定期全量快照，文件小恢复快，可能丢失最近数据；AOF 追加每条写命令（appendfsync 策略权衡丢失窗口），数据更完整。生产通常 RDB+AOF 混合（4.0+），兼顾恢复速度与完整性。

## q_c008_09
- type: choice
- kp: 分布式锁
- difficulty: medium
- score: 5
- stem: 用 SETNX 实现分布式锁，"加锁与设置过期时间必须原子化"的正确命令是？
- options: A) SETNX key value 再 EXPIRE key B) SET key value NX EX 10 C) INCR key D) GETSET
- answer: B

## q_c008_10

## q_c008_13
- type: short
- kp: 缓存一致性
- difficulty: hard
- score: 10
- stem: 【面试题】为什么推荐"先更新数据库再删除缓存"，而不是"先删缓存再更新数据库"或"更新缓存"？
- keywords: 并发交错, 回填旧值, 概率, 最终一致, 延迟双删
- analysis: 先删缓存后更新库：删除后到更新完成前，读请求会把旧值重新回填缓存，且写库耗时越长概率越大，不一致风险高。先更新库再删缓存：不一致仅出现在"读请求恰好拿到旧值且回填晚于删除"的小概率交错，配合延迟双删或 binlog 订阅删除可进一步压缩。更新缓存（而非删除）：并发写容易互相覆盖产生脏数据，且可能写入了从未被读的数据浪费资源，删除让下次读被动加载更简单可靠。

## q_c008_14
- type: short
- kp: 分布式锁
- difficulty: hard
- score: 10
- stem: 【面试题】手写 SETNX 分布式锁有哪些坑？Redisson 分别如何解决？
- keywords: 原子性, 误删, 续期, 可重入, 唯一标识
- analysis: 坑 1：SETNX 与 EXPIRE 分开执行宕机死锁 → Redisson 用 Lua 原子加锁并设过期。坑 2：业务超时锁先过期被他人抢占 → 看门狗自动续期。坑 3：删锁误删他人的锁 → 加锁存唯一标识（UUID+线程 ID），释放用 Lua 校验后再删。坑 4：不可重入 → hash 结构记录持有者与重入次数。坑 5：自旋轮询浪费 → Pub/Sub 订阅解锁消息唤醒等待者。

## q_c008_17
- type: short
- kp: 持久化
- difficulty: medium
- score: 10
- stem: AOF 的三种刷盘策略（appendfsync）分别是什么？如何权衡数据安全与性能？
- keywords: always, everysec, no, 丢失窗口, 性能
- analysis: always：每条命令刷盘，最多丢 1 条命令，性能最差；everysec（默认）：每秒刷盘一次，最多丢 1 秒数据，性能与安全的折中；no：交给操作系统，性能最好但丢失窗口不可控。选型：金融类用 always 或混合持久化，一般业务 everysec 足够，配合主从复制进一步降低丢失风险。

## q_c008_18
- type: short
- kp: 缓存策略
- difficulty: medium
- score: 10
- stem: 什么是旁路缓存（Cache Aside）与读写穿透（Read/Write Through）？Redis 实践中为何旁路模式最常见？
- keywords: 应用层, 回填, 删除, 同步, 库
- analysis: 旁路缓存：应用自己维护缓存与库——读未命中回填、写先库后删缓存，缓存与应用解耦，Redis 客户端生态最成熟。读写穿透：缓存层作为唯一入口，由缓存组件同步读写库，应用不感知两份数据，需要缓存中间件支持。Redis 实践选旁路的原因：实现简单可控、可以按业务定制 key/TTL/不一致容忍度，且 Redis 本身不提供到数据库的穿透能力。

## q_c008_19
- type: short
- kp: 面试
- difficulty: medium
- score: 10
- stem: 【面试题】Redis 的过期删除策略与内存淘汰策略分别是什么？
- keywords: 惰性删除, 定期删除, LRU, LFU, maxmemory
- analysis: 过期删除：惰性删除（访问时检查过期）+ 定期删除（周期性随机抽检过期 key），平衡 CPU 与内存。内存淘汰：达到 maxmemory 时按策略淘汰，noeviction（拒绝写，默认）、allkeys-lru（全键 LRU）、volatile-lru（仅过期键）、allkeys-lfu（访问频率）等。热点缓存用 allkeys-lru/lfu；淘汰策略必须按业务数据重要性选择。

## q_c008_20
- type: short
- kp: 面试
- difficulty: hard
- score: 10
- stem: 【面试题】如何保证 Redis 与数据库的最终一致？描述基于 binlog 的方案。
- keywords: Canal, binlog, 订阅, 删除缓存, 重试
- analysis: 方案：应用正常"先更新库再删缓存"之外，再挂 binlog 订阅组件（如 Canal）伪装成 MySQL 从库，捕获数据变更事件 → 投递到 MQ → 消费者删除对应缓存（失败重试队列兜底）。优点：与业务代码解耦，覆盖所有写入口（含批量任务、人工修数），保证最终一致。要点：删除而非更新缓存、幂等消费、处理 MQ 延迟窗口内的短暂不一致。
