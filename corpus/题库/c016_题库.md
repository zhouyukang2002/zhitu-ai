## q_c016_01
- type: choice
- kp: 秒杀架构
- difficulty: medium
- score: 5
- stem: 秒杀系统的核心设计原则是？
- options: A) 尽量让所有请求到达数据库 B) 逐层过滤流量，把请求拦在离用户最近的地方 C) 提高数据库配置 D) 只用缓存不用数据库
- answer: B
- analysis: 漏斗模型：前端静态化+按钮防抖 → 网关限流 → Redis 预扣 → MQ 削峰 → 数据库乐观锁兜底。层层过滤后真正到数据库的请求只有少量成功订单。

## q_c016_02
- type: choice
- kp: 库存预扣
- difficulty: hard
- score: 5
- stem: Redis 预扣库存的 Lua 脚本为什么必须用 Lua？
- options: A) Lua 更快 B) "判断库存充足再扣减"两步需要原子执行，Lua 脚本在 Redis 单线程内原子运行 C) Lua 支持事务回滚 D) 语法要求
- answer: B
- analysis: 先 GET 判断再 DECR 是两步操作，并发下交错会超卖；Lua 脚本在 Redis 中原子执行判断+扣减+记录用户，无法被其他命令插入。等价方案是单命令 DECR 后判负回补，但 Lua 更干净。

## q_c016_03
- type: choice
- kp: 异步下单
- difficulty: medium
- score: 5
- stem: Redis 预扣成功后，订单创建为什么走 MQ 异步而不是同步写库？
- options: A) MQ 更安全 B) 消费端按数据库能力匀速落单，削峰且用户快速得到"排队中"反馈 C) MQ 便宜 D) 减少代码

## q_c016_04
- type: choice
- kp: 库存预扣
- difficulty: medium
- score: 5
- stem: 数据库层防止超卖的兜底 SQL 是？
- options: A) UPDATE stock SET num = num - 1 WHERE id = 1 B) UPDATE stock SET num = num - 1 WHERE id = 1 AND num > 0 C) SELECT num FROM stock WHERE id = 1 D) DELETE FROM stock WHERE id = 1
- answer: B
- analysis: 带 num > 0 条件的原子 UPDATE（乐观思想）：库存不足时影响行数为 0，判断受影响行数决定成败，任何并发下都不会减到负数。A 无条件扣减会超卖。

- stem: 【面试题】"Redis 预扣 100 件、最终 DB 只卖 99 件"的不一致如何发生与解决？
- keywords: 回补失败, 消息丢失, 对账, TTL, 最终一致

## q_c016_18

- keywords: 对账任务, DB 为准, 回补, 幂等修正, 人工复核

## q_c016_19
