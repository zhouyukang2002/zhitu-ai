## q_c049_09
- type: choice
- kp: 冲突处理
- difficulty: hard
- score: 5
- stem: git rebase 与 merge 的历史差异是？
- options: A) 相同 B) rebase 把提交移到目标分支顶部形成线性历史，merge 产生合并提交保留真实分叉 C) rebase 更安全 D) merge 会丢提交
- answer: A
- analysis: 团队约定：本地个人分支用 rebase 保持整洁，公共分支合入用 merge（或 squash）；已推送的公共分支禁止 rebase（改写他人历史）。
## q_c049_10

- stem: .gitignore 的正确使用时机是？
- options: A) 提交后想忽略再加 B) 项目初始化时配置（构建产物/密钥/本地配置），已追踪文件需先 rm --cached C) 只对远端生效 D) 无用

## q_c049_11
- type: short
- kp: Git 基础
- difficulty: hard
- score: 10
- stem: 【面试题】git merge 与 git rebase 的区别及团队使用约定。
- keywords: 合并提交, 线性历史, 公共分支, 黄金法则, 冲突
- analysis: merge 保留真实分叉历史（产生 merge commit），rebase 重放提交形成线性历史（整洁但改写提交）。约定：私有分支 rebase 主干保持整洁；已推送共享分支永不 rebase（黄金法则，会破坏他人基于旧历史的提交）。冲突处理频率 rebase 逐个提交解决，merge 一次性解决。
## q_c049_12
- type: short
- kp: 冲突处理
- difficulty: hard
- score: 10
- stem: 【面试题】提交了包含密钥的文件到公共仓库，如何彻底处理？
- keywords: 立即作废, 历史清理, filter-repo, 强制推送, 协作通知
- analysis: 1) 第一优先：立即作废/轮换密钥（比清理历史更紧急——历史已可能被拉取）；2) 历史清理：git filter-repo 或 BFG 从全部提交中移除文件，force push；3) 通知协作者重新 clone/rebase；4) 复盘：.gitignore 预置 + 提交钩子扫描密钥。要点：轮换凭证优先于历史清理。
## q_c049_13

- keywords: 发布分支, 持续交付, 小步快跑, 特性开关, 团队规模

## q_c049_15
- type: short
- kp: 分支策略
- difficulty: hard
- score: 10
- stem: 【面试题】多人协作时如何避免"合并地狱"？给出流程与工具建议。
- keywords: 小步合入, 频繁同步, 主干健康, 特性开关, 自动化
